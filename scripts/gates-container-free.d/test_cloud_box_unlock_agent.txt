# 2026-10-23 (C-Series Cloud, the customer holds the disk key): the unlock agent, on the stand-in cryptsetup. Enrolling needs the setup code and an open, unclaimed vault, and answers the recovery key once; confirming needs that key and starts the claim in a unit nothing stops; a wrong key is refused and recorded, on the plain disk with the source's /24 or /48 only and bounded; the right one opens the Host's ports and starts its services; five tries a minute per source; key changes need a key; a claim cut off after the bootstrap key went is finished by an unlock with a customer key; JSON over a real unix socket. No device, no root. The handoff: POST /api/setup takes the code and email as a form from the account site's origin or the page's own only, answers a 303 and a __Host- SameSite=Strict cookie and keeps only its hash; the cookie stands for the code on enroll and confirm from the page's own origin only (not an app of the Host, not without an Origin); confirm takes the key the page showed back (I saved it) and starts the claim only while that is the key waiting, so a second tab's enroll makes the first tab's confirm refused; the owner ticket goes without a key only to the browser whose claim set the keys up (not one whose claim stopped before it) and only to make the owner, with a key as a sign-in once there is one; the Host reads only its hash; /api/setup-code is gone; once the setup is done the code hands nothing over; the page's own calls with the handoff's cookie are no tries (two tabs in one minute finish the setup), a typed code and a key still count; the redirect and cookie over the socket. The box has /var/log/journal before its vault is made, so the test runs where mkdir with S_ISGID is refused (RestrictSUIDSGID). A stop (the updater's try-restart) answers the request in hand, then exits; between requests at once; the unit's KillMode=mixed (no real signal: the handler is called on the serving thread).
